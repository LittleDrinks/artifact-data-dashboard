# Feature Specification: 环境配置与系统变量治理

**Feature Branch**: `001-env-config-cleanup`  
**Created**: 2026-01-03  
**Status**: Draft  
**Input**: User description: "整理项目环境配置与系统变量，减少环境变量冲突，统一本地/容器/开发与生产配置方式，并完善文档与启动脚本"

## Clarifications

### Session 2026-01-03

- Q: “生产（或类生产）启动”的验收范围以哪种运行形态为准？ → A: 以 `docker-compose.yml` + 生产模式变量为准
- Q: 本项目“开发者手动配置的变量”的首选承载方式是什么？ → A: 仓库根目录 `.env`（不提交）+ `.env.example`（提交）作为主入口
- Q: 当同一配置项在多个来源同时存在时，采用哪一种统一优先级规则？ → A: 启动参数/显式覆盖 > 环境变量（含从 `.env` 注入）> 代码内默认值
- Q: 本次治理的验收覆盖范围包含哪些组件？ → A: 全栈（`frontend` + `backend` + `docker-compose.yml` 中相关数据服务）
- Q: “诊断报告/配置生效摘要”的输出渠道是什么？ → A: 仅 stdout（启动时打印；容器通过日志获取）

### User Story 1 - 新成员可快速启动项目 (Priority: P1)

作为新加入项目的开发者，我希望按照一份清晰的指引完成本地运行所需的配置，而不需要到处找零散的系统变量/脚本参数，避免“能跑但不知道为什么能跑”。

**Why this priority**: 直接影响上手效率与协作成本；当前“环境配置相当混乱”会导致启动失败、重复排障和知识孤岛。

**Independent Test**: 在一台“没有历史配置”的机器/用户账号上，仅依照文档完成配置后即可成功启动并完成一次端到端的基础验证（例如访问主页并完成一个最小业务查询/展示）。

**Acceptance Scenarios**:

1. **Given** 新开发者没有任何项目相关系统变量与缓存配置，**When** 按照文档完成必要配置并启动，**Then** 项目可稳定运行且不需要临时修改系统变量来“碰运气”。
2. **Given** 新开发者配置缺失或填写错误，**When** 尝试启动，**Then** 系统会清晰指出缺失/冲突项及修复建议，而不是以模糊错误或静默失败结束。

---

### User Story 2 - 开发者可明确切换运行模式 (Priority: P2)

作为日常开发者，我希望在“开发/生产（或相近）”等不同运行模式之间切换时，配置来源与优先级是明确且可预测的，避免上一次的变量残留影响当前运行。

**Why this priority**: 模式切换是常见操作；可预测性不足会带来隐蔽 Bug、误用数据源和排障成本上升。

**Independent Test**: 在同一台机器上先后用两种模式启动，系统对每次启动采用的配置来源给出清晰说明且不互相污染。

**Acceptance Scenarios**:

1. **Given** 机器上存在历史配置残留，**When** 切换运行模式并启动，**Then** 系统使用预期的配置集合与优先级，且可通过可见输出确认“当前生效配置来自哪里”。
2. **Given** 两个配置来源对同一配置项提供了不同值，**When** 启动，**Then** 系统按既定优先级选择并提示发生了覆盖（避免无声覆盖）。

---

### User Story 3 - 排障更直接 (Priority: P3)

作为维护者/协作者，我希望在遇到启动或连接问题时，能够快速定位是“配置缺失/冲突/不兼容”还是“服务不可用/网络问题”，并用统一的排障路径减少来回沟通。

**Why this priority**: 这类问题高频且耗时；统一诊断输出与排障指南能显著降低支持成本。

**Independent Test**: 人为制造典型配置错误（缺失、冲突、不合法值），系统能输出一致、可操作的诊断信息与下一步建议。

**Acceptance Scenarios**:

1. **Given** 必要配置缺失，**When** 启动，**Then** 诊断输出包含：缺失项清单、用途解释、如何补齐（不泄漏敏感值）。
2. **Given** 配置值格式不合法或不兼容，**When** 启动，**Then** 诊断输出包含：错误项、期望格式、示例（使用占位符）。

---

### Edge Cases

- 配置来源同时存在且互相矛盾（例如同一项在多个地方被赋值）。
- 运行模式切换后仍残留上一次的值导致“看似成功但实际指向错误数据/服务”。
- 必要配置缺失时：必须快速失败并给出可执行的修复步骤。
- 配置中包含敏感信息：输出日志/诊断时不得泄漏完整敏感值。
- 不同操作系统/终端下启动方式不一致导致的误用（例如脚本行为差异）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 定义并公开“配置来源的层级与优先级”，使同一配置项在不同来源同时存在时结果可预测。
- **FR-001a**: 优先级规则 MUST 为：启动参数/显式覆盖 > 环境变量（含从 `.env` 注入）> 代码内默认值。
- **FR-002**: 系统 MUST 提供一份“最小可运行配置清单”，包含每个配置项的用途说明、是否必填、示例值（使用占位符）。
- **FR-002a**: 系统 MUST 以仓库根目录的 `.env`（不提交）+ `.env.example`（提交）作为“开发者手动配置变量”的主入口与示例模板。
- **FR-003**: 系统 MUST 在启动时对“必填项缺失、值格式不合法、明显冲突”进行校验，并给出可操作的错误信息。
- **FR-004**: 系统 MUST 提供统一的诊断输出，用于显示：当前运行模式、哪些配置来源被检测到、哪些配置项发生了覆盖（不显示敏感值原文）。
- **FR-004a**: 诊断输出 MUST 在启动时打印到标准输出（stdout）；不要求写入文件或依赖独立的 Debug API/页面。
- **FR-005**: 系统 MUST 确保敏感配置不会被写入版本库中的默认配置文件与示例输出；示例与日志必须脱敏。
- **FR-006**: 用户 MUST 能通过文档与标准化启动方式完成：本地开发启动、生产（或类生产）启动。
- **FR-006a**: 上述启动方式 MUST 覆盖 `frontend`、`backend` 以及由 `docker-compose.yml` 管理的相关数据服务，且配置项命名与来源规则在各组件间一致。
- **FR-007**: 系统 MUST 明确“允许/不允许”的配置方式（例如：哪些配置只能在运行前设定，哪些可在运行时修改并生效）。
- **FR-008**: 文档 MUST 提供常见故障排查路径（缺失配置、冲突覆盖、连接失败、权限不足），并与诊断输出保持一致的术语。

### Requirement Acceptance Criteria

- **AC-FR-001**: 当同一配置项在多个来源中同时存在时，系统会按以下优先级做出确定选择：启动参数/显式覆盖 > 环境变量（含从 `.env` 注入）> 代码内默认值。
- **AC-FR-001a**: 诊断报告能指出该配置项最终取值来自哪一类来源（至少到“启动参数/环境变量/默认值”的粒度），并在发生覆盖时提示“更高优先级覆盖了更低优先级”。
- **AC-FR-002**: 存在一份面向使用者的清单，能够让新开发者识别“哪些配置必须提供、为什么需要、如何提供（示例用占位符）”。
- **AC-FR-002a**: 仓库中存在 `.env.example`，覆盖“最小可运行配置清单”中需要开发者提供的所有配置项；示例值使用占位符且不包含真实敏感值。
- **AC-FR-002b**: 文档明确说明 `.env` 不应提交到版本库，并给出新开发者从 `.env.example` 生成本地 `.env` 的步骤。
- **AC-FR-003**: 对于缺失、格式不合法、明显冲突三类问题，启动会被阻止并输出可操作的修复信息（包含问题定位与下一步）。
- **AC-FR-004**: 每次启动都可以获得一份诊断摘要，至少包括运行模式、检测到的配置来源、覆盖发生的配置项列表；摘要不包含敏感值原文。
- **AC-FR-004a**: 本地运行时诊断摘要可在控制台直接看到；容器运行时诊断摘要可通过容器日志查看（例如通过容器日志命令获取）。
- **AC-FR-005**: 任意默认文件/示例输出中不出现真实敏感值；日志与诊断对敏感字段进行一致的脱敏处理。
- **AC-FR-006**: 文档中存在两条清晰的启动路径（本地开发与生产/类生产），按步骤执行即可完成启动与最小验证。
- **AC-FR-006a**: “生产/类生产”启动以 `docker-compose.yml` 为入口，通过“生产模式变量”选择该模式；不要求使用 `docker-compose.prod.yml`。
- **AC-FR-006b**: 在全栈范围内（`frontend` + `backend` + 数据服务）执行上述两条启动路径时，诊断摘要能够分别覆盖并解释各组件的关键配置来源与覆盖关系（允许按组件分段输出）。
- **AC-FR-007**: 文档明确列出哪些配置允许在运行中变更、哪些必须在运行前设定；与系统实际行为一致。
- **AC-FR-008**: 排障指南覆盖至少：缺失配置、冲突覆盖、连接失败、权限不足；并与诊断输出中的术语与字段名保持一致。

### Key Entities *(include if feature involves data)*

- **运行模式**: 表示一次运行所处的配置集合（例如开发/生产/测试等），决定默认值与校验规则的集合。
- **配置项**: 一条可被读取的配置值（例如连接信息、端口、特性开关等），包含：名称、用途、是否敏感、是否必填、默认值（如适用）。
- **配置来源**: 提供配置项的渠道（例如系统级设置、项目级配置文件、启动参数等），包含：优先级与适用范围。
- **诊断报告**: 启动/排障时生成的可读摘要，描述当前生效配置的来源与覆盖关系（脱敏）。

### Measurable Outcomes

- **SC-001**: 新开发者从“零配置”到完成首次成功启动的时间 ≤ 15 分钟（按文档操作，不需要额外口头指导）。
- **SC-002**: 启动失败时，≥ 90% 的失败可被归因到明确的配置项问题（缺失/冲突/格式错误），并在一次失败输出中给出修复建议。
- **SC-003**: 运行模式切换的可预测性：连续两次不同模式启动，生效配置摘要中不出现“来源不明”的值，且覆盖关系可追溯。
- **SC-004**: 环境配置相关的重复排障沟通次数下降 ≥ 50%（以 issue/群聊重复问答为衡量）。

## Assumptions

- 本特性面向“项目贡献者/维护者”的可维护性与可运行性治理，不改变核心业务功能。
- 项目存在至少两类运行场景：本地开发与生产（或类生产）运行。
- 项目包含前后端与数据服务等多个组件，环境配置需要跨组件协调。

## Scope (In / Out)

**In Scope**:

- 统一配置来源、优先级、命名与文档术语。
- 统一“开发者手动配置变量”的入口：仓库根目录 `.env` + `.env.example`。
- 统一启动路径与说明（包含本地与生产/类生产）。
- 增强启动前校验与诊断输出（脱敏）。
- 覆盖范围包含 `frontend`、`backend` 与 `docker-compose.yml` 中的相关数据服务。

**Out of Scope**:

- 引入全新的部署平台或运行架构。
- 将 `docker-compose.prod.yml` 作为本特性的验收前提（本特性以 `docker-compose.yml` + 生产模式变量为准）。
- 迁移/重建现有数据或修改业务数据模型。

## Dependencies

- 需要确认当前各组件实际使用的配置来源与关键配置项集合（作为治理的输入）。
- 需要维护者确认“生产/类生产”的目标运行形态与发布习惯，以便文档与优先级规则一致。
