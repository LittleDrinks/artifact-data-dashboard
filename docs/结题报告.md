## 一、项目背景与意义

文化遗产数字化是国家文化战略的重要方向。《"十四五"文化发展规划》明确提出要加强文化遗产数字化保护与传承，推动文物资源的开放共享与智能应用。传统的文物数据管理以表格录入为主，数据孤立、缺乏关联分析能力，检索方式单一、无法支持语义化查询，可视化程度低、难以直观理解文物间的关系网络，智能化程度不足、依赖人工处理大量数据。

本项目"文物大数据与人工智能集成系统"旨在解决上述痛点，构建一个集数据管理、知识图谱、智能问答于一体的文化遗产数据平台。项目的核心定位是"人机协作"——AI 不是黑盒顾问，而是可观察、可干预的工具插件，人类专家和 AI 助手共享同一套工具，协作过程完全透明。

本项目的意义在于：（1）探索文化遗产数据的数字化管理范式，为博物馆、文物局等机构提供可复用的技术方案；（2）验证知识图谱技术在文物领域的应用价值，实现实体关系的可视化探索；（3）展示大语言模型（LLM）在垂直领域的落地路径，实现有据可查、有源可溯的智能问答；（4）践行"AI 透明化"理念，让用户理解 AI 的推理过程和决策依据。

## 二、研究内容与目标

### 2.1 研究内容

本项目的核心研究内容包括四个方面：

**（1）统一文物数据管理平台**。建立覆盖文物元数据全生命周期的管理系统，包括数据录入、检索、统计、导出等功能。数据模型涵盖 14 个字段：名称、描述、类别、年代、出土地点、收藏机构、材质、尺寸、图片链接、标签、来源链接等。支持关键词搜索和多维度筛选（年代、类别、地点），实现分页浏览和详情查看。

**（2）知识图谱可视化探索**。构建基于文物实体关系的知识图谱，展示文物与年代、类别、地点、材质等实体的语义关联。采用 D3.js 力导向图实现交互式可视化，支持节点拖拽、画布缩放平移、关键词搜索高亮、节点类型筛选等功能。实现三级数据源 fallback 架构（Neo4j → LightRAG KV Store → SQLite），确保数据可用性。

**（3）AI 智能问答集成**。基于大语言模型（LLM）构建领域问答系统，采用 ReAct（Reasoning + Acting）Tool Calling 架构，让 AI自主决定调用检索工具获取真实数据。回答附带引用来源，用户可点击跳转验证数据准确性。采用 SSE（Server-Sent Events）流式输出，展示 Thinking（推理过程）、Tool Call（工具调用）、Answer（最终回答）三阶段，实现 AI 可观察性。

**（4）人机协作核心理念**。所有功能同时暴露为标准化 REST API，供 AI Agent 调用，人类用户和 AI 助手共享同一数据和服务层。图像修复功能展示 AI 工具作为插件集成到平台的理念，用户绘制遮罩指定修复范围，系统调用 OpenCV inpainting 算法执行修复。

## 三、技术方案与实现

### 3.1 技术栈选型

本项目采用前后端分离架构，技术栈选型如下：

| 层级 | 技术 | 版本 | 选型理由 |
|------|------|------|----------|
| 前端 | Vite + React + TypeScript | React 19 | 高性能构建工具，组件化开发，类型安全 |
| UI 框架 | Ant Design Pro | AntD 5 | 企业级组件库，开箱即用的图表和布局 |
| 后端 | Python FastAPI | 3.12 | 高性能异步框架，自动 OpenAPI 文档 |
| AI 框架 | LangChain + LightRAG | LangChain 0.3 | 工具调用编排，RAG 索引构建 |
| 关系数据库 | SQLite（WAL 模式） | - | 轻量级、零配置、适合单机部署 |
| 图数据库 | Neo4j | 5.x | 专业图数据库，支持 Cypher 查询 |
| 认证 | JWT（bcrypt） | - | 无状态认证，安全密码哈希 |

### 3.2 系统架构设计

系统采用分层架构设计：

```
┌─────────────────────────────────────────┐
│           前端层（React + AntD）          │
│  Dashboard │ Artifacts │ Graph │ Chat   │
└─────────────────────────────────────────┘
                    ↕ REST API + SSE
┌─────────────────────────────────────────┐
│           后端层（FastAPI）               │
│  Routers → Services → Models            │
└─────────────────────────────────────────┘
                    ↕
┌─────────────────────────────────────────┐
│           数据层                          │
│  SQLite │ Neo4j │ LightRAG KV Store     │
└─────────────────────────────────────────┘
                    ↕
┌─────────────────────────────────────────┐
│           AI 服务层                       │
│  DeepSeek API │ LangChain Tools         │
└─────────────────────────────────────────┘
```

### 3.3 知识图谱三级 Fallback 架构

为确保知识图谱数据可用性，设计了三级 fallback 数据源：

```
Level 1: Neo4j（语义图谱）— 优先使用图数据库
    ↓ 如果无数据或不可用
Level 2: LightRAG KV Store（JSON 文件）— LLM抽取的语义关系
    ↓ 如果文件不存在
Level 3: SQLite（结构化属性关系）— 文物表字段派生关系
```

**Level 3 SQLite fallback** 从 artifacts 表派生关系：每件文物生成 `artifact_X` 节点，根据 era/category/location/tags 字段生成对应节点，并创建"属于朝代"、"属于类别"、"出土于"等关系边。这确保即使 Neo4j 和 LightRAG 均不可用，图谱仍能展示基本关系网络。

### 3.4 混合知识图谱构建策略

采用规则三元组 + LLM 语义抽取的混合策略：

**（1）规则三元组生成**。通过 Python脚本从文物元数据自动提取结构化关系：

| 关系类型 | 三元组模式 | 数据来源 |
|----------|-----------|----------|
| 属于朝代 | (文物, 属于朝代, 年代) | artifacts.era 字段 |
| 属于类别 | (文物, 属于类别, 类别) | artifacts.category 字段 |
| 出土于 | (文物, 出土于, 地点) | artifacts.location 字段 |
| 包含标签 | (文物, 包含标签, 标签) | artifacts.tags 字段 |

规则三元组共生成 **4220 条关系**，覆盖所有 771 件文物。

**（2）LLM 语义三元组抽取**。使用 LightRAG 框架，调用 GLM-4 API 从文物描述文本中抽取语义实体和关系。配置参数：

```python
LightRAG(
    working_dir=settings.LIGHTRAG_DIR,
    llm_model_func=lambda prompt: call_glm_api(prompt),
)
```

抽取结果存储在 `kv_store_full_entities.json` 和 `kv_store_full_relations.json` 文件中，包含 LLM 发现的非结构化语义关系（如"后母戊鼎与妇好墓相关"）。

### 3.5 ReAct Tool Calling AI 问答

AI 智能问答采用 ReAct（Reasoning + Acting）架构，LLM自主决定调用检索工具：

**（1）工具定义**：

| 工具名 | 功能 | 参数 |
|--------|------|------|
| search_artifacts | 搜索文物数据库 | keyword, era, category, limit |
| get_artifact_detail | 获取文物详情 | artifact_id |
| query_knowledge_graph | 查询知识图谱 | keyword, limit |

**（2）Tool Calling 流程**：

```
用户提问 → LLM 推理 → 决定调用工具 → 执行检索 → 
获取结果 → LLM 综合回答 → 附带引用来源
```

最多支持 5 轮 ReAct 循环，LLM 可连续调用多个工具完成复杂查询。

**（3）System Prompt 设计**：

```
你是一个专业的文物知识助手...
回答规则：
- 用户询问文物相关信息时，务必先调用工具查询数据库
- 综合工具返回的数据回答，用编号列表组织内容
- 引用数据时标注来源，用户可点击验证
```

### 3.6 SSE 流式响应

采用 Server-Sent Events（SSE）实现流式输出，事件类型包括：

| 事件 | 说明 |
|------|------|
| thinking_start/delta/end | AI推理过程（deepseek-reasoner） |
| tool_call_start/result | 工具调用开始和结果 |
| answer_start/delta/end | 最终回答生成 |
| done | 完成信号，附带sources |

前端使用 `fetch() + ReadableStream` 手动解析 SSE 事件（因 POST请求需发送 body），实现 AbortController 支持用户中途取消生成。

### 3.7 图像修复（OpenCV Inpainting）

图像修复功能展示 AI 工具插件化集成理念：

**（1）用户交互**：Canvas 绘制遮罩，白色区域标记破损位置
**（2）算法选择**：支持 TELEA 和 Navier-Stokes 两种 OpenCV inpainting 算法
**（3）前后对比**：展示修复前/后图片对比效果
**（4）认证保护**：POST端点需 JWT token，防止未授权使用

## 五、创新点

### 5.1 混合知识图谱构建策略

本项目创新性地采用"规则三元组 + LLM 语义抽取"混合策略构建知识图谱：

**创新价值**：
- 规则三元组覆盖率高、质量可控，确保所有文物都有基础关系
- LLM语义抽取发现非结构化关系（如"后母戊鼎与妇好墓相关"），弥补规则覆盖不足
- 两层数据互补，既保证完整性又提升语义深度

**技术实现**：
- 规则层：Python 脚本从元数据字段派生，生成 4220 条结构化关系
- 语义层：LightRAG 框架调用 GLM-4 API，从描述文本抽取实体和关系

### 5.2 AI 透明可观察设计

本项目践行"AI 不是黑盒"理念，实现三阶段透明展示：

**创新价值**：
- Thinking阶段展示推理过程，用户理解 AI 如何分析问题
- Tool Call阶段展示检索工具、查询参数、结果数量，验证数据来源
- Sources阶段提供引用来源，点击跳转文物详情，数据准确性可追溯

**用户体验**：
- 不同于普通 AI聊天，用户能"看懂"AI 的工作过程
- 学术/文物领域需要严谨性和可验证性，透明设计契合专业需求

### 5.3 人机协作设计理念

本项目核心创新理念：AI 是工具插件，不是独立顾问

**设计原则**：
- 所有功能同时暴露为 REST API，人类用户和 AI Agent 共享同一接口
- AI 调用的 search_artifacts 工具与人类使用的 /api/artifacts 端点相同
- 数据来源统一、验证路径统一、协作过程透明

**实际体现**：
- Chat 页面 AI 调用工具后，用户可点击来源跳转详情页验证
- 图像修复功能展示插件化集成（用户绘制遮罩 → OpenCV 执行）
- 未来可扩展：AI 辅助数据录入，人工审批确认

### 6.2 遇到的挑战和解决方案

**挑战一：POST SSE 流式响应**
- 问题：浏览器 EventSource API 只支持 GET 请求，无法发送 body 和 header
- 解决：使用 `fetch() + ReadableStream` 手动解析 SSE 事件流

**挑战二：Python 版本兼容**
- 问题：系统默认 Python 3.9 不支持 `X | None` 语法（3.10+ 特性）
- 解决：创建基于 Python 3.12 的虚拟环境

**挑战三：知识图谱数据源**
- 问题：Neo4j 未部署时图谱无数据
- 解决：设计三级 fallback架构（Neo4j → LightRAG → SQLite），确保数据可用

**挑战四：Windows 编码问题**
- 问题：open() 读取含中文 JSON 默认 GBK 编码，报 UnicodeDecodeError
- 解决：所有文件操作显式指定 `encoding='utf-8'`

**挑战五：AbortController 资源泄漏**
- 问题：SSE 流式响应中途断开时连接未关闭
- 解决：实现 AbortController，组件卸载/切换会话时 abort 请求
