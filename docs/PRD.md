# 文物大数据与人工智能集成系统 — 产品需求文档 (PRD)

> **文档定位**：产品需求、用户故事、项目成果。技术实现细节见 `docs/specs/*.md`。
> 最后更新：2026-04-20

---

## 1. 项目背景与目标

### 1.1 背景

文化遗产数字化是国家文化战略的重要方向。传统文物数据管理面临三大痛点：

- **数据孤立，缺乏关联**：记录彼此独立，无法挖掘历史关联、地理联系、工艺传承等深层关系
- **检索单一，语义缺失**：仅支持关键词搜索，无法理解"商代青铜器主要出土于哪些地区"等语义意图
- **可视化程度低**：文物关系网络复杂，纯文本列表难以直观呈现

### 1.2 项目定位

**文物大数据与人工智能集成系统** — 一个人机协作的文化遗产数据平台。让人类专家和 AI 助手共享同一套工具：数据查询、知识图谱、图像修复等功能，既有直观的界面面板，也有标准化接口供 AI 调用，协作过程完全透明。

核心哲学：**AI 不是黑盒顾问，而是可观察、可干预的协作者。**

### 1.3 目标

1. 建立统一的文物数据管理平台，覆盖数据录入、检索、统计、导出全流程
2. 构建基于知识图谱的文物实体关系可视化，支持交互式探索
3. 提供基于大语言模型的智能问答能力，展示 AI 作为工具插件的理念
4. 所有功能同时暴露为标准化接口，供 AI Agent 调用，人机共享同一数据和服务层

## 2. 核心创新点

### 2.1 混合知识图谱构建策略

- **规则三元组**：从元数据字段自动生成，覆盖所有 771 件文物，保证基础关系的完整性和准确性
- **LLM 语义抽取**：利用 LightRAG 从描述文本发现非结构化关系（如"后母戊鼎与妇好墓相关"），弥补规则无法覆盖的深层语义关联
- 两层数据互补，既保证覆盖率又提升语义深度

### 2.2 AI 透明可观察设计

当前 AI 应用普遍是"黑盒"。本项目设计"思考过程 → 工具调用 → 最终回答"三阶段透明展示：

- 用户可以看到 AI 如何理解问题、决定调用什么工具、查询什么参数、获得什么数据、如何组织回答
- 回答附带来源引用，用户可点击跳转验证
- 解决了 LLM 在专业领域应用的核心痛点——可信度问题

### 2.3 人机协作设计理念

将 AI 定位为"工具插件"而非"独立顾问"。系统中所有功能同时暴露为标准化接口：

- 人类用户通过 Web 页面访问
- AI 助手通过工具调用访问（集成文物检索、详情查询、知识图谱查询三个工具）
- 两者共享同一数据源、同一服务层、同一验证机制

### 2.4 可扩展的系统集成架构

图像修复功能以"插件"方式接入系统：

- 后端仅需约 125 行 Python 代码（框架代码约 32 行，算法逻辑约 60 行）
- 通过标准化 REST API 接口封装 OpenCV inpainting 算法
- 前端以 440 行 TypeScript 实现遮罩绘制和前后对比交互
- 接入新算法只需替换核心调用（如将 cv2.inpaint 替换为 LaMa、IOPaint），框架代码可完全复用

## 4. 功能模块需求

### 4.1 用户认证与账户管理

**User Stories**:
- US-1.1: 作为新用户，我想要注册账户，以便使用系统的全部功能
- US-1.2: 作为已注册用户，我想要通过用户名/邮箱登录，以便访问我的个人工作空间
- US-1.3: 作为管理员，我想要通过 JWT Token 保护敏感操作，防止未授权访问

**验收标准**:
- AC-1.1: 注册需填写用户名、邮箱、密码（至少 8 位）
- AC-1.2: 登录成功后获取 JWT Token，跳转到首页
- AC-1.3: 未登录用户访问需要认证的页面时，自动跳转登录页

**详细技术规格**：见 `specs/auth.md`

### 4.4 AI 智能问答

## 5. 项目成果

### 5.1 数据成果

| 指标 | 目标 | 实际 | 状态 |
|------|------|------|------|
| 有效文物记录 | ≥700 条 | 771 条 | ✅ |
| 知识图谱节点数 | ≥500 个 | 1362 个 | ✅ |
| 知识图谱关系数 | ≥1000 条 | 4220 条 | ✅ |
| 功能页面数 | 6 个 | 7 个（含知识抽取页） | ✅ |

### 5.2 数据资产

- 年代类型 15 种（新石器时代、商、周、汉、唐、宋等）
- 类别类型 8 种（青铜器、陶瓷、玉器、书画、金银器等）
- 收藏机构 50 余家（故宫博物院、国家博物馆、湖南博物院等）
- 节点类型 5 种（文物、年代、类别、地点、标签）
- 关系类型 4 种（属于朝代、属于类别、出土于、包含标签）

### 5.3 执行过程

**前期（立项至中期）**：数据采集与初步开发。团队学习网络爬虫技术，采集原始数据。同步搭建系统基础框架，实现用户登录、文物列表、知识图谱可视化等初步功能。但数据质量参差不齐，AI 服务尚未集成。

**后期（中期至结题）**：方向调整与集中开发。数据策略从"追求数量"转向"注重质量"，以国家文物局"禁止出境展览文物"名录为锚点，对 771 条记录进行系统化清洗。技术路线从"自研算法"转向"集成创新"，将成熟技术（LangChain 工具调用、LightRAG 语义抽取、OpenCV 图像修复）以模块化方式集成。架构全面重构，采用 FastAPI + React + Neo4j 技术栈。

### 5.4 经验与教训

1. **方向调整**：从"自研算法"到"集成平台"——前期在算法自研上走了弯路，但对问题域的深入理解为后期架构决策奠定了基础
2. **数据策略**：从"追求数量"到"注重质量"——原始采集 2485 条，过滤非文物条目 138 条（17.9%），最终保留 771 条有效记录，其中高质量核心文物 168 件
3. **不足**：数据覆盖面有限（771 条 vs 故宫 186 万件）；图像修复为 Demo 级实现

## 6. 非功能性需求

### 6.1 性能要求

- **API 响应**：普通 CRUD 接口 < 500ms；统计聚合接口 < 2s
- **AI 问答首字节**：SSE 流式首 token 返回 < 3s
- **图谱渲染**：500 节点以内的流畅交互
- **安全超时**：AI 问答 60s 无数据自动终止

### 6.2 安全要求

- **认证**：JWT Token 认证（24h 过期）
- **密码**：bcrypt 哈希存储
- **限流**：登录接口 60s 内最多 5 次尝试
- **SQL 注入防护**：全部使用参数化查询

### 6.3 可用性要求

- **优雅降级**：图数据库不可用时降级处理，不影响基础文物管理功能
- **AI 服务降级**：AI API 不可用时 Chat 页面显示友好提示，不阻塞历史查看
- **错误处理**：统一错误响应格式，前端展示友好错误提示
- **移动端基本可用**：768px 以下侧边栏自动收起，核心功能可操作
- **资源清理**：前端组件卸载时清理 SSE 连接、定时器等资源
