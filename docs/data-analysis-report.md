# 文物数据采集策略分析——从需求到方案

> 本文档为「文物大数据与人工智能集成系统」数据层的设计论证。
> 从智能问答模块的业务需求出发，逐步推导：需要什么数据 → 覆盖什么范围 → 从哪获取 → 如何衡量质量 → 下一步做什么。
> 每个决策点标注假设和不确定之处，方便答辩时回应质疑。

---

## 第一章：智能问答需要什么数据？

### 1.1 从业务场景反推

本系统的核心功能：用户用自然语言提问关于中国文物的问题，系统给出基于事实的回答。

典型问题（按难度递增）：

| 类型 | 示例问题 | 需要什么数据 |
|------|---------|------------|
| 单实体查询 | "四羊方尊是什么时候的？" | 该文物的年代字段 |
| 筛选聚合 | "商代有哪些著名的青铜器？" | 所有文物的年代+类别字段 |
| 跨实体比较 | "越王勾践剑和夫差剑有什么区别？" | 两件文物的描述文本 |
| 关联推理 | "和四羊方尊一起出土的还有哪些？" | 文物间的关联关系 |
| 开放问答 | "为什么司母戊鼎改名为后母戊鼎？" | 足够长的描述文本 |

这说明我们需要**三类数据**协同工作：

1. **文本语料**（description / full_text）—— RAG 检索的核心，直接喂给 LLM 生成回答
2. **结构化元数据**（年代、类别、地点、材质…）—— 支持精确筛选和知识图谱
3. **关系数据**（文物-朝代、文物-博物馆、文物-文物）—— 支持图谱可视化和多跳推理

### 1.2 数据字段需求

**必须有的**（没有就没法做演示）：name、text（≥200字）、era（标准朝代名）、category

**应该有的**（显著提升演示效果）：location、museum、image、tags

**有了更好的**（锦上添花）：material、dimensions、related_items

## 第二章：覆盖什么范围？——不是拍脑袋，而是有分级体系

你指出"高价值"这个说法缺乏依据，这是对的。中国的文物有官方分级制度，我们可以据此定义覆盖优先级。

### 2.1 中国文物分级体系

中国的可移动文物共 **1.08 亿件/套**（第一次全国可移动文物普查，2017），按价值分为：

| 等级 | 数量 | 说明 |
|------|------|------|
| 一级文物 | 21.8 万件 | "特别重要历史、艺术、科学价值" |
| 二级文物 | 55 万件 | "重要历史、艺术、科学价值" |
| 三级文物 | 308 万件 | "比较重要历史、艺术、科学价值" |
| 一般文物 | 其余 | 普通藏品 |

> 来源：文化部《文物藏品定级标准》（2001）

在这个金字塔的最顶端，是国家文物局公布的 **"禁止出境展览文物"**（共三批）：

| 批次 | 发布时间 | 数量 | 内容 |
|------|---------|------|------|
| 第一批 | 2002-01 | 64件（组） | 综合类 |
| 第二批 | 2012-06 | 37件（组） | 书画专用 |
| 第三批 | 2013-07 | 94件（组） | 综合类 |
| **合计** | | **195件（组）** | 全部为一级文物 |

> 来源：国家文物局，完整名单见 [维基百科](https://zh.wikipedia.org/wiki/禁止出境展览文物)

**这 195 件就是我们数据覆盖的第一优先级。** 它们全部是一级文物中的顶级，每一件都有明确的官方认定，公众知名度最高，答辩演示时评委最可能问到。

### 2.2 覆盖优先级分层

基于官方分级体系，我们定义四层覆盖目标：

| 优先级 | 覆盖范围 | 数量 | 来源 | 目标覆盖率 |
|--------|---------|------|------|-----------|
| **T1（必须）** | 禁止出境展览文物 | 195件 | 国家文物局官方名单 | ≥95%（185+件） |
| **T2（应该）** | 各大博物馆"镇馆之宝" | ~100件 | 各博物馆官方公布 | ≥80% |
| **T3（理想）** | 一级文物中的知名条目 | 数千件 | 维基百科"中国文物"分类 | 尽可能多 |
| **T4（后续）** | 二三级文物、地方馆藏 | 百万级 | 专业数据库 | 暂不涉及 |

**T2 镇馆之宝参考来源**：

- 中国国家博物馆"古代中国"展：后母戊鼎、四羊方尊、人面鱼纹彩陶盆、击鼓说唱俑 等（来源：[中国国家博物馆 - 维基百科](https://zh.wikipedia.org/wiki/中国国家博物馆)）
- 故宫博物院：清明上河图、千里江山图、五牛图、各种釉彩大瓶 等（来源：[故宫博物院 - 维基百科](https://zh.wikipedia.org/wiki/故宫博物院)）
- 湖北省博物馆"四大镇馆之宝"：曾侯乙编钟、越王勾践剑、郧县人头骨化石、元青花四爱图梅瓶（来源：[湖北省博物馆 - 维基百科](https://zh.wikipedia.org/wiki/湖北省博物馆)）
- 陕西历史博物馆：舞马衔杯银壶、兽首玛瑙杯、鎏金银铜竹节熏炉 等（来源：[陕西历史博物馆 - 维基百科](https://zh.wikipedia.org/wiki/陕西历史博物馆)）
- 湖南博物院：马王堆系列（T型帛画、素纱襌衣、漆器）、大禾方鼎、皿方罍 等（来源：[湖南博物院 - 维基百科](https://zh.wikipedia.org/wiki/湖南省博物院)）

### 2.3 当前覆盖评估

**T1（禁止出境展览文物）**：数据集 category 为"禁止出境展览文物"的有 174 条，但其中约 30-40 条是朝代名、博物馆名等非文物条目（混入原因见第三章）。去重后实际覆盖约 **140/195 = 72%**。

**缺失的知名文物**（举几个重要的）：

| 文物 | 知名度 | 缺失原因 |
|------|--------|---------|
| 秦始皇兵马俑 | 极高 | 爬虫未爬取"秦始皇陵"分类 |
| 唐三彩系列 | 高 | 未爬取"唐三彩"分类 |
| 司南、地动仪 | 高（教科书常客） | 未爬取"中国古代科学仪器"分类 |
| 铜车马 | 高 | 可能在"秦始皇陵"分类中 |
| 部分书画作品 | 高 | 第二批书画未完整爬取 |

> **不确定之处**：我们目前没有将数据集逐条对照完整的 195 件官方名单。这需要人工校对——拿到官方 PDF 名单，在数据集中逐一搜索确认。这是数据清洗前的必要步骤。

## 第三章：为什么选维基百科？——以及它混入了什么

### 3.1 数据源对比

| 数据源 | 数据量 | 结构化 | 获取难度 | 中文 | 免费 |
|--------|--------|--------|---------|------|------|
| **中文维基百科** | ~1000+ 文物条目 | 高（infobox+分类） | 低（MediaWiki API） | 好 | 是 |
| 国家文物局平台 | 1亿+件 | 高 | 极高（无公开API，需审批） | 好 | 是 |
| 故宫数字文物库 | 62.8万件 | 高 | 高（无API，需爬取） | 好 | 是 |
| Wikidata | 与维基同源 | 很高（三元组） | 低 | 一般（英文为主） | 是 |
| 百度百科 | 大量 | 低（无infobox） | 高（反爬严格） | 好 | 是 |
| CNKI | 海量 | 低（非结构化） | 高（付费） | 好 | 否 |

**选择维基百科的核心原因**：有免费 API、数据有结构、中文覆盖好、内容有编辑审核。对于大创项目，这是获取成本最低、数据质量最高的来源。

### 3.2 混入了什么？——这是 bug 还是 feature？

爬虫从维基分类页获取所有子页面，导致混入了约 39 条非文物条目：

| 类型 | 示例 |
|------|------|
| 朝代/时期 | 商代、西周、战国、唐朝、明朝… |
| 博物馆 | 中国国家博物馆、磁州窑富田遗址博物馆… |
| 列表页 | 两汉金质官印列表、文革时期文物损毁列表… |
| 机构/法律 | 国家文物局、中华人民共和国文物保护法… |

**关键设计问题：这些"非文物"应该删除，还是保留为知识图谱节点？**

我的建议是**给现有表加一个 `node_type` 字段，二者兼得**。

当前架构分析（查了代码后的结论）：
- `backend/app/services/graph.py` 已经在运行时动态构建图谱——从 artifacts 表生成节点和边，era/category/location 自动成为节点类型
- `frontend/src/pages/Graph.tsx` 已经按 `TYPE_COLORS` 渲染不同类型的节点
- 也就是说，**架构上已经支持多类型节点**，只是数据表没区分

改动方案：给 `artifacts` 表加两个字段：

```python
# backend/app/models/artifact.py — 只加 2 行
node_type: Mapped[str] = mapped_column(String(20), default="artifact")   # artifact / dynasty / museum / ...
properties_json: Mapped[Optional[dict]] = mapped_column(JSON, default=None)  # 类型专属属性
```

这样：
- **文物管理页面**加一个 `WHERE node_type = 'artifact'` 过滤（改动 ~15 行）
- **知识图谱页面**不需要改（已经按类型渲染）
- 朝代、博物馆、地点这些节点自然出现在图谱中，增强连接密度
- 总改动量：约 **50 行**，不影响现有功能

> **假设 H1**：朝代和博物馆作为知识图谱节点，可以显著提升图谱的连接密度和可读性。但需要额外处理这些节点的属性和关系。
>
> **注意**：可扩展性是我们的一大卖点——数据模型应该容易适配新数据源。加 `node_type` 列而不是建新表，保持了向后兼容，同时为未来接入故宫、国博等数据源预留了空间。

## 第四章：infobox 格式不统一怎么办？——接受差异，用技术手段处理

### 4.1 问题具体表现

不同维基条目的 infobox 字段名完全不同：

| 文物 | infobox 字段名 |
|------|---------------|
| 四羊方尊 | 时代、出土、现藏、入录 |
| 翠玉白菜 | 艺术家、年份、媒介、尺寸、收藏地、藏主、登录号 |
| 刀币 | （无 infobox） |
| 后母戊鼎 | 时代、出土、现藏、入录 |

"年代"可能叫"时代"、"年份"、"时期"；"地点"可能叫"出土"、"收藏地"、"位置"。你说的对——这不是我们的问题，而是数据源的客观现实。故宫做了 10 多年的知识图谱项目（你提到的叶祎佩分享），他们面临的也是同样的问题。

### 4.2 两种技术路线

**路线 A：规则映射**（我们之前用的方式）

写一个字段映射表：`{"时代": "era", "年份": "era", "时期": "era", "出土": "location", "收藏地": "location", ...}`

- 优点：确定性高、速度快、不依赖 API
- 缺点：维护成本高，遇到新格式要手动加规则；无法处理非标准表述

**路线 B：用小参数 LLM 做知识抽取**（推荐）

给 LLM 一段 prompt："从以下维基百科信息中，提取文物的年代、出土地点、收藏机构、材质、尺寸，输出 JSON。" 然后把 infobox 原文 + 正文前几段一起喂给它。

- 可用模型：Qwen2.5-7B（[Qwen2.5 技术报告, arXiv:2412.15115](https://arxiv.org/abs/2412.15115) 显示其在信息抽取任务上表现优秀）
- 部署方式：Ollama 本地部署（`ollama run qwen2.5:7b`），RTX 4060 Laptop（8GB VRAM）可运行 Q4 量化版本（约占 4.5GB）
- 优点：自动适应各种格式，不需要维护映射表；还能从正文中抽取 infobox 里没有的信息（如材质、尺寸）
- 缺点：输出格式不完全可控（可加 JSON schema 约束）；7B 模型抽取质量弱于 32B+

**建议**：路线 B。理由是：

1. 我们的 infobox 格式差异是客观存在的，且未来补充新数据源（故宫、国博）时差异只会更大
2. 抽取 prompt 只需要写一次，后续新增数据源时无需修改
3. Qwen2.5-7B 可以在消费级 GPU 上运行（或通过 API 调用），成本可控
4. 抽取结果可以人工抽检验证质量

**抽取准确率评估方法**：

从 195 件禁止出境展览文物中**抽样 30-50 件**，手动从维基百科页面抄写 ground truth（年代、地点、博物馆、材质），然后让 Qwen 抽取同一批，按字段算 F1：

```
精确率 = LLM 抽出的字段中正确的比例
召回率 = 应该抽出的字段中 LLM 实际抽到的比例
F1 = 2 × 精确率 × 召回率 / (精确率 + 召回率)
```

如果 F1 ≥ 0.85，可以接受；低于 0.85 则需要优化 prompt 或换更大的模型。

> **假设 H2**：Qwen2.5-7B 对中文文物 infobox 的字段抽取 F1 ≥ 0.85。需抽样实测验证。

### 4.3 从结构化抽取到知识图谱——引入 LightRAG

LLM 抽取不仅限于"从 infobox 提取字段"，还可以进一步用它来构建**知识图谱**。这里就是我们技术栈中 LightRAG 的切入点。

**LightRAG**（[Guo et al., 2024, arXiv:2410.05779](https://arxiv.org/abs/2410.05779)，已被 EMNLP 2025 接收）是一个基于图结构增强的 RAG 框架。它的核心能力：

1. **从文本中自动抽取实体和关系**，构建知识图谱
2. **双层检索**：低层（具体实体关系）+ 高层（主题概览），既回答具体问题也能做总结
3. **增量更新**：新数据可以增量添加到图谱中

**LightRAG 在本项目中的定位**——它不是一个"替代 Qwen 抽取"的工具，而是在抽取之上的一层：

```
原始数据（维基 infobox + 正文）
        ↓
  Qwen2.5-7B 结构化抽取（era, location, museum, material...）
        ↓                    ↓
  填充数据库字段        输出三元组（实体-关系-实体）
        ↓                    ↓
  前端展示/筛选         LightRAG 构建知识图谱
                             ↓
                      图谱增强的智能问答
```

具体来说，LightRAG 能做的事：

1. **从正文抽取 infobox 之外的关系**：四羊方尊正文提到"与大禾方鼎同为商代方尊"，LightRAG 可以抽取出 `(四羊方尊, 同时期同类, 大禾方鼎)` 这种关联
2. **跨文档连接**：不同文物页面中提到的同一人物、同一地点、同一事件，LightRAG 会自动关联
3. **图谱增强检索**：用户问"和四羊方尊同时期的青铜器有哪些"，LightRAG 的图检索能沿着 `(四羊方尊) → 属于朝代 → (商) ← 属于朝代 ← (其他青铜器)` 路径找到答案

**LightRAG 的 GPU 需求**：

LightRAG 官方推荐用 32B+ 模型做实体关系抽取（最佳质量），但也支持配置为使用任何 LLM 后端。我们的方案：
- **优先方案**：LightRAG 后端配置为调用 DeepSeek API（复用现有的 AI_API_KEY），不在本地跑大模型
- **备选方案**：用 Ollama 的 Qwen2.5-7B 做轻量抽取（质量略低，但不依赖外部 API）

> **假设 H3**：LightRAG + DeepSeek API 从文物描述中抽取的三元组，质量足够构建有意义的知识图谱。需要实测——用 50 条文物描述做抽取，人工评估三元组的准确性和完整性。

## 第五章：如何评价问答效果？——benchmark 设计

### 5.1 评价框架

学术界已有成熟的 RAG 评价框架，我们直接采用：

**RAGAS**（Retrieval Augmented Generation Assessment，[Es et al., 2023](https://arxiv.org/abs/2309.15217)）提供四个核心指标：

| 指标 | 测量什么 | 直觉解释 |
|------|---------|---------|
| **Faithfulness** | 回答是否基于检索到的上下文 | 有没有编造 |
| **Answer Relevancy** | 回答是否切题 | 有没有答非所问 |
| **Context Precision** | 检索到的文档中相关内容的比例 | 检索准不准 |
| **Context Recall** | 回答所需的信息是否都被检索到 | 检索全不全 |

**ARES**（[Saad-Falcon et al., NAACL 2024](https://arxiv.org/abs/2311.09476)）进一步支持自动生成测试数据，减少人工标注成本。

### 5.2 测试问题从哪来？

你问的问题很关键：测试问题不是凭空编的，需要逼近真实业务场景。我提出三种来源，按可信度排序：

**来源 1：从知识库自动生成**（RAGAS 的做法）

从每条文物的结构化数据中，用规则或 LLM 自动生成问题：
- 有年代 → "XX是什么时候的文物？"
- 有出土地 → "XX是在哪里出土的？"
- 有收藏机构 → "XX现在收藏在哪里？"
- 从三元组 (文物, 朝代, 商) → "哪些文物属于商代？"

优点：覆盖全面，可量化。缺点：偏向简单问题，不反映真实用户行为。

**来源 2：从领域论文中提取**（推荐作为补充）

文化遗产 + 知识图谱问答已有学术研究，虽然我们未在 arXiv 上找到完全匹配的论文（文化遗产领域论文多发表于 IEEE/ACM 等会议），但可以从以下方向获取参考：

- 博物馆数字人文领域的研究（如 MuseNet、ChatMuseum 等，发表于 LREC-COLING 等会议）提供了博物馆场景下的典型问题类型
- [CRUD-RAG（arXiv:2401.17043）](https://arxiv.org/abs/2401.17043)：中文 RAG 基准，覆盖创建/读取/更新/删除四类任务，其中的"读取"任务最贴近我们的问答场景

从这些论文的实验设置中提取他们使用的测试问题类型和分布，作为我们 benchmark 的参考。

**来源 3：从真实用户行为收集**（长期方案）

系统上线后记录用户问题，标注哪些问题系统回答得好/不好，持续优化。大创项目阶段不适用，但可以在答辩时作为"未来工作"提及。

**我的建议**：来源 1 作为主 benchmark（可自动化，覆盖全面），来源 2 作为补充（更贴近学术评价标准）。

### 5.3 回答完整度如何评价？

| 评价维度 | 方法 | 自动化程度 |
|---------|------|-----------|
| 检索是否找对了文档 | Context Recall（RAGAS） | 全自动 |
| 回答有没有编造 | Faithfulness（RAGAS） | 全自动 |
| 回答是否切题 | Answer Relevancy（RAGAS） | 全自动 |
| 回答是否包含关键信息 | 需要人工定义"关键信息点"，用 LLM 判断覆盖了几个 | 半自动 |
| 回答是否流畅、有帮助 | 人工评价 5 分制 | 人工 |

### 5.4 Benchmark 数据量

参考 CRUD-RAG（[Lyu et al., 2024, arXiv:2401.17043](https://arxiv.org/abs/2401.17043)）和 RAGAS 的实践，一个领域 RAG benchmark 通常需要 200-500 个测试问题。对于大创项目演示，建议准备 **100 个问题**：

- 50 个自动生成（来源 1）
- 30 个手动编写（覆盖复杂问题、比较问题、推理问题）
- 20 个从论文/真实场景改编（来源 2）

## 第六章：数据量需要多少？——有论文支撑

### 6.1 学术参考

Liu et al. (2023) 在 ["Lost in the Middle: How Language Models Use Long Contexts"](https://arxiv.org/abs/2307.03172)（TACL 2023）中发现：

> **关键结论：LLM 在处理长上下文时，相关信息放在开头或结尾效果最好，放在中间会显著降低性能。增加更多检索文档不总是有帮助。**

这直接说明了 RAG 系统中检索质量的重要性——不是返回越多文档越好，而是要精准地返回最相关的文档。

Gao et al. (2024) 在 ["Retrieval-Augmented Generation for Large Language Models: A Survey"](https://arxiv.org/abs/2312.10997) 中总结：

> **检索 top-5 到 top-10 篇文档通常是最佳的，返回更多文档反而可能引入噪声导致性能下降。**

LightRAG（[Guo et al., 2024, arXiv:2410.05779](https://arxiv.org/abs/2410.05779)）通过图结构增强检索，在保持低计算成本的同时提高了检索精度——这验证了"结构化数据比海量数据更有价值"的思路。

### 6.2 我们的目标

基于以上研究，结合大创项目的演示定位：

| 维度 | 目标 | 依据 |
|------|------|------|
| 有效文物数 | **1000-1500 条** | 满足 RAG 语料下限，覆盖 T1+T2 |
| T1 覆盖率 | **≥95%**（185+/195） | 答辩演示的"保底"要求 |
| 文本质量 | **≥90% 有 ≥200 字描述** | 文档质量 > 数量 |
| 元数据完整性 | 年代 ≥70%，地点 ≥50% | 支撑筛选和图谱 |

> **答辩话术**："我们依据 Liu et al. (2023) 和 Gao et al. (2024) 的研究结论，聚焦于提高数据集质量而非盲目扩大规模。同时引入 LightRAG（Guo et al., 2024）的图增强检索，目标 1000-1500 条高质量文物数据，覆盖 95% 以上的国家一级保护文物（禁止出境展览文物）。"

## 第七章：数据清洗 vs 爬取——先做什么？

你说的对，应该**先爬完，再统一清洗**。理由：清洗逻辑（年代归一化、去重、非文物过滤）要在看到完整数据后才能设计得准确。如果先清洗再爬新数据，新数据可能需要重新清洗。

### 7.1 执行顺序

```
Phase 1: 补充爬取（扩大覆盖面）
   ├── 爬取缺失的维基分类（兵马俑、书画、唐三彩、科学仪器…）
   ├── 深度爬取图片（从页面内所有图片中选择）
   ├── 爬取维基分类标签（页面底部的 Categories）
   └── 爬取参见链接（关联文物）
   预期：629 → 1000-1500 条

Phase 2: 知识抽取（统一处理格式差异）
   ├── 用 Qwen2.5-7B 对每条数据做结构化抽取
   ├── 输出：era, location, museum, material, dimensions, tags
   ├── 同时从正文补充 infobox 没有的信息
   └── 人工抽检 50-100 条验证准确率
   预期：元数据填充率大幅提升

Phase 3: 数据清洗（去重、归一化、过滤）
   ├── 年代归一化（76种 → 15种标准朝代）
   ├── 去除非文物条目（或重构为知识图谱节点）
   ├── 清除文本中的维基标记 [1][a]
   └── 去重（同一文物在不同分类下的重复）
   预期：数据质量达到 benchmark 要求

Phase 4: 构建 benchmark + 评测
   ├── 自动生成 50 个测试问题
   ├── 手动编写 30 个复杂问题
   ├── 从论文改编 20 个问题
   └── 用 RAGAS 框架评测，输出四个指标
   预期：有量化数据支撑答辩
```

### 7.2 LightRAG 语料准备与实验

LightRAG 需要**长文本语料**来抽取知识三元组。我们的 `full_text` 字段（平均 ~1000 字）就是输入语料。但需要注意：

1. **文本必须干净**：维基引用标记 `[1]` 会影响抽取质量 → Phase 3 清除
2. **文本需要足够长**：太短（<200字）的条目抽不出有意义的关系 → Phase 2 补充
3. **覆盖需要全面**：LightRAG 的图谱质量取决于语料覆盖面 → Phase 1 扩大覆盖

LightRAG 实验流程：
```
干净语料 → LightRAG 抽取三元组（后端用 DeepSeek API）
         → 构建知识图谱 → 与维基分类+Qwen抽取的图谱对比
         → 评估哪种方法的关系质量更高
```

LightRAG 在文化遗产领域已有先例：
- [towards-lightrag-sensibility-cultural-heritage-llm-framework](https://github.com/baalguan/towards-lightrag-sensibility-cultural-heritage-llm-framework)（MIT 开源，文化遗产专用框架）
- GraphRAG vs LightRAG 在博物馆编目任务中的对比研究（Zotero, CSCW 2025）
- MDPI Sustainability (2024) 发表的 RAG 方法在文化遗产知识图谱中的应用

> **注意**：LightRAG 的实验依赖干净语料，所以必须在 Phase 3（文本清洗）之后进行。但它不依赖 Phase 2 的结构化抽取——LightRAG 自己会做实体关系抽取。两条路线可以并行。
